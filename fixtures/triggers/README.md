# triggers-research

Docs-derived fixtures for simulci's `triggers.ts`. Every row carries `rule`, `source` (the docs.github.com page URL, anchored via YAML aliases at the top of each file) and `quote` (the sentence copied verbatim, including docs typos). Test cases that the docs state outright are unmarked; cases the docs only imply carry `derived: true`; things the docs do not settle are marked `UNVERIFIED` inline. All four pages were fetched on 2026-10-17 (raw HTML via curl, converted to text, sentences grepped verbatim).

## types-defaults.yml

For each of the 19 events that have activity types, the full type list and the default when `types:` is omitted. Only two events have a non-"all" default: `pull_request` and `pull_request_target` default to `[opened, synchronize, reopened]`; every other typed event defaults to all types (the events page repeats the same sentence per event, quoted per row). `repository_dispatch` types are user-defined `event_type` strings. The 14 type-less events are listed too; the docs do not say what GitHub does with a stray `types:` under one of them (UNVERIFIED). Extra per-event trigger suppressions that a simulator must model are attached as `extra_rules` (merge-conflict PRs, draft releases, `inactive` deployment statuses, Actions-created check suites, more-than-three-tags pushes, `requested` not firing on re-run).

## default-branch-only.yml

The 21 events carrying the sentence "This event will only trigger a workflow run if the workflow file exists on the default branch." (branch_protection_rule, check_run, check_suite, delete, discussion, discussion_comment, fork, gollum, issue_comment, issues, label, milestone, page_build, public, registry_package, repository_dispatch, schedule, status, watch, workflow_dispatch, workflow_run), each with its GITHUB_REF cell. Two of them run with a non-default GITHUB_REF: `workflow_dispatch` (the dispatched branch/tag) and `registry_package` (branch/tag of the package). `pull_request_target` has no such note but its prose says it runs "in the context of the default branch". Ambiguities: (1) the docs do not say whether a `workflow_dispatch` against a non-default ref executes the default-branch copy or the ref's copy of the file (UNVERIFIED); (2) `image_version` has no note yet its GITHUB_REF is the default branch; (3) `create` has no note, so the file on the created ref is what runs.

## ref-per-event.yml

The events-page table columns `GITHUB_SHA` / `GITHUB_REF` for all 33 events, copied cell-for-cell, plus a derived `simulated_ref` shape, plus the contexts-page sentences for `github.ref`, `ref_name`, `ref_type`, `base_ref`, `head_ref`, `event_name`, `sha` with cases. UNVERIFIED: the literal `refs/heads/gh-readonly-queue/...` format for `merge_group` is not on these pages ("Ref of the merge group" is all they say); `ref_type` for a `refs/pull/N/merge` ref (docs list only `branch`|`tag`); `event_name` inside a `workflow_call`-ed workflow. CONFLICT: the events table gives `pull_request_target` GITHUB_REF as "Default branch" while the contexts page says "the `ref` from the base branch"; the fixture uses the base branch and flags it.

## filters.yml

The complete filter-pattern cheat sheet as `{pattern, path|ref, matches}` cases (every verbatim example match for branches/tags and for paths), the six pattern operators (`*` no-slash, `**` any, `?` and `+` as regex-style quantifiers on the preceding character, `[]` with a-z/A-Z/0-9 ranges, leading `!`), ordered negation with the docs' own `releases/**` / `!releases/**-alpha` and `sub-project/**` / `!sub-project/docs/**` examples, `refs/heads/` and `refs/tags/` prefix handling (patterns are matched against the short ref name; `branches` only ever sees branch refs, `tags` only tag refs), `pull_request` branches matching the BASE branch, `merge_group` branches matching the TARGET branch (not the queue ref), `paths` = any-file-matches vs `paths-ignore` = all-files-match, empty diff = no run, "path filters are not evaluated for pushes of tags", branches AND paths = both must hold, push with only branches/only tags never fires for the other ref kind, every "cannot use both X and X-ignore" sentence, and the workflow_run branches filter. UNVERIFIED: the docs never literally say "either branches or tags matches" for a push with both filters; the fixture derives OR-across-ref-kinds from the example list and the "undefined Git ref" sentence. UNVERIFIED: whether "not evaluated for pushes of tags" means the tag push runs (fixture assumes yes). The `paths` section claims only `*` and `**` are accepted for paths while the cheat sheet uses `?` and `!` in path examples; fixture follows the cheat sheet.

## skip-ci.yml

The five bracket markers plus the two `skip-checks` trailer forms, where they are read (the pushed commit message; the PR's HEAD commit), and that only `push` and `pull_request` honour them (`pull_request_target` is the docs' explicit counter-example). The claim that `workflow_dispatch` can be used to run anyway is NOT stated on the skip page; it follows from "Skip instructions only apply to the `push` and `pull_request` events" and is marked derived. UNVERIFIED: which commit of a multi-commit push is inspected (docs say "the commit message in a push"); case sensitivity and whitespace tolerance of the markers; what happens when `skip-checks` is not the last trailer.

## dispatch-inputs.yml

Input types `boolean | choice | number | environment | string` (workflow_call: `boolean | number | string`, where `type` is required), the limit of 25 top-level inputs and 65,535 payload characters (sentence quoted with the docs' stray space before the period), `default`/`required`, and context typing: the docs promise only that the `inputs` context "preserves Boolean values as Booleans" and that `github.event.inputs` stringifies them; `choice` resolves to a string. UNVERIFIED: that a `number` input is a JS number in `inputs` (inferred from the contexts page's type cell and its `"build_id": 123456768` example, which is a workflow_call example); that omitted dispatch inputs get `false`/`0`/`""` (that sentence is written for workflow_call only); whether `type` is required on a dispatch input; whether a non-option `choice` value sent via API is rejected.

## workflow-run.yml

`workflows` (list of workflow `name`s, OR-ed, glob patterns incl. the escaped `Build C\+\+` example), `types` `[completed, requested, in_progress]` default all with `requested` absent on re-runs, `branches`/`branches-ignore` constraining the branch the triggering workflow ran on (with the docs' example where `main` is excluded), mutual exclusion, "triggered regardless of the conclusion" with `github.event.workflow_run.conclusion` gating, the default-branch requirement with GITHUB_REF = default branch, the three-level chain limit, and artifact access. UNVERIFIED: whether `workflows` is required; the full enumeration of `conclusion` values; what "branch the triggering workflow ran on" is for a tag- or PR-triggered upstream run; whether `*` in a workflow-name glob stops at `/`.

## Not covered (out of scope of the four pages)

Concurrency, `paths` behaviour for `merge_group`, the `image_version` `names`/`versions` glob semantics beyond the one example, and Enterprise-Managed-User scheduling rules (quoted only where they touch `schedule` defaults).
